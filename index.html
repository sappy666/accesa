01

La accesibilidad amplía la experiencia.

No existe una única forma de ver, escuchar, comprender o interactuar con una interfaz. Diseñar alternativas reduce barreras permanentes, temporales y situacionales.

Visual

Contraste, escalado, estructura, alternativas textuales y contenido que no dependa solo del color.

Motriz

Objetivos táctiles cómodos, teclado, orden de foco y controles que toleren distintas formas de interacción.

Auditiva

Subtítulos, transcripciones y señales visuales equivalentes para la información sonora.

Cognitiva

Lenguaje claro, navegación predecible, jerarquías consistentes y menor carga innecesaria.

02

Cuatro principios para orientar decisiones.

POUR resume la base de WCAG: el contenido debe ser perceptible, operable, comprensible y robusto.

P

Perceptible

La información puede percibirse de más de una manera.

O

Operable

La interfaz funciona con distintas entradas, incluido teclado.

U

Comprensible

Contenido, navegación y errores son claros y predecibles.

R

Robusto

El contenido conserva significado con tecnologías de asistencia.

04

Los componentes necesitan todos sus estados.

Normal, hover, foco, activo, error, carga y deshabilitado forman parte del mismo componente accesible.

<button type="button" aria-describedby="ayuda">Continuar</button> <p id="ayuda">Revisa tus datos antes de continuar.</p>
05

Diseñar accesible también significa probar.

Las herramientas automáticas ayudan, pero no sustituyen pruebas manuales ni evaluación con personas.

Teclado

Recorre la página usando Tab, Shift + Tab, Enter, Space y Escape.

Zoom

Aumenta el contenido y comprueba que nada importante quede oculto o cortado.

Lector de pantalla

Revisa nombres accesibles, orden de lectura, headings, landmarks y estados.

Automatización

Usa auditorías como apoyo para detectar contraste, semántica y errores frecuentes.

06

Accesibilidad no significa diseñar menos.

“Arruina la estética”

Una jerarquía clara, buen contraste y estados consistentes pueden reforzar el sistema visual.

“Es una capa final”

Muchas barreras nacen en arquitectura, contenido, diseño de interacción y componentes.

“Un plugin lo resuelve”

Las preferencias de visualización pueden ayudar, pero no reemplazan una base accesible.

08

Código base listo para pegar.

Pequeños patrones que puedes reutilizar directamente en un proyecto HTML/CSS.

Variables y foco visible

Tokens básicos, tamaño táctil, texto escalable y soporte para movimiento reducido.

:root { --text: #111318; --background: #F6F7F9; --accent: #5747DB; --focus: #145CFF; } body { font: 1rem/1.5 Inter, system-ui, sans-serif; color: var(--text); background: var(--background); } button, a, input, select { min-height: 44px; } :focus-visible { outline: 3px solid var(--focus); outline-offset: 3px; } @media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: .01ms !important; transition-duration: .01ms !important; } }

Botón con nombre claro

<button type="button" aria-describedby="saveHelp"> Guardar cambios </button> <p id="saveHelp">Guarda tu configuración actual.</p>

Campo con error asociado

<label for="email">Correo electrónico</label> <input id="email" type="email" aria-invalid="true" aria-describedby="emailError"> <p id="emailError" role="alert">Ingresa un correo válido.</p>

Enlace para saltar contenido

<a class="skip-link" href="#main">Saltar al contenido</a> <main id="main">...</main>
09

Tres prompts para auditar tu proyecto con IA.

Pega tu HTML, CSS o componente después del prompt. Úsalos como apoyo: una revisión automática no reemplaza pruebas manuales ni con tecnologías de asistencia.

01

Auditoría completa

Para detectar barreras antes de publicar.

Actúa como especialista en accesibilidad web. Revisa el código que te entregaré usando WCAG 2.2 como referencia. Identifica problemas de semántica, contraste, teclado, foco, formularios, imágenes, ARIA, zoom, responsive y movimiento. Para cada hallazgo indica: problema, impacto para la persona usuaria, criterio relacionado y corrección concreta. No inventes errores: separa lo confirmado de lo que requiere prueba manual.
02

Corregir el código

Para pasar del diagnóstico a una implementación.

Revisa este componente y devuélveme una versión corregida y lista para pegar. Conserva su apariencia visual tanto como sea posible, pero mejora HTML semántico, navegación por teclado, foco visible, nombres accesibles, labels, mensajes de error, áreas táctiles, contraste y reduced motion. Explica brevemente cada cambio y evita ARIA innecesario cuando exista un elemento HTML nativo equivalente.
03

Plan de pruebas

Para comprobar lo que el código no demuestra.

Crea un plan de QA de accesibilidad para esta interfaz. Organízalo por teclado, lector de pantalla, zoom/reflow, contraste, formularios, contenido multimedia, orientación y movimiento. Incluye pasos reproducibles, resultado esperado y qué revisar manualmente. Prioriza barreras que bloquean tareas y termina con una checklist breve para desktop y móvil.

Checklist antes de publicar.

Una revisión rápida para detectar barreras comunes antes de entregar una interfaz.

Contraste suficiente para texto y controles.
Navegación completa mediante teclado.
Foco visible y orden lógico.
Labels persistentes y errores descriptivos.
Texto alternativo cuando aporta significado.
Headings y landmarks con estructura coherente.
Contenido usable con zoom y en pantallas pequeñas.
Movimiento reducido cuando la persona lo solicita.
